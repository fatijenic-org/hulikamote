How one picture is handled

The steps (in the code today)

GPU work CPU work (striped in the charts) Dashed box = runs only when a violation needs it (one vehicle at a time, on every 5th picture)

The camera gives about 30 pictures a second. The detector runs on 1 of every 3. The chart shows only those pictures.

Step times (ms, examples)

NOW: one worker does every step, one picture at a time

The GPU waits while the worker does the CPU steps (striped). The next picture does not start until the last one ends.

PROPOSAL: a work line, and two trackers side by side

  • A reads and finds the vehicles. It already works on picture 6 while the rest handle picture 5.
  • The vehicle tracker and the people tracker do not need each other. They run at the same time.
  • B updates the vehicle history, runs the extra models (only if on) and checks the rules.
  • C makes the JPEG and sends it.

Same models, same rules, same tickets in the same order. Each tracker still sees the pictures in order.

What limits the gain

  • The slowest worker sets the speed. If A is slow, A is the limit.
  • Plain Python cannot run in two places at once. GPU and image work can. If the rules are the slow part, we need a second process.
  • A, B and C each take memory for pictures in transit. A small queue (2 pictures) keeps it low.

Plan

  • 1. Timer on each step. Writes times in the log. No change in behavior.
  • 2. Split into A / trackers / B / C. Decide with the real numbers from step 1.
  • 3. If the GPU steps dominate: FP16 or TensorRT, and batch the tiles.
