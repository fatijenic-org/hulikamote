First principles

Start here: what a camera really sends

A video is not a special thing. It is many still pictures, called frames, shown one after the other, about 25 every second. A network camera takes those pictures and sends them over the network to anyone who asks. Sending them while they are being filmed, instead of saving a file, is called a stream.

To ask for a stream you need only one thing: where the camera is. That is its address, made of an IP address, a port and a path, for example rtsp://192.168.1.20:554/stream1. HULI-KAMOTE is the one asking. So from our side, a CCTV camera, a phone and a laptop playing a clip are the same thing: an address that gives back pictures.

IdeaWhat it means for the system
The camera only sends picturesWe never control the camera (no turning or zooming). We only read.
It is addressed, like a websiteOnly the address changes when a real CCTV replaces our stand-in. The rest of the system does not change.
The network can failCameras get switched off and Wi-Fi drops. The system must notice, say so in words, and reconnect by itself.
The AI can be slower than the cameraIf the AI needs more time than 40 ms per frame, old frames pile up and the picture falls behind. We keep only the newest.

About these sources

The Hikvision and Dahua paths agree across vendor and installer pages, but many are third-party, and ports and paths can differ by model and firmware, so the camera's own manual decides. The sources also disagree on which video format ONVIF Profile S makes mandatory, so read the ONVIF specification itself before quoting that detail.

Where the system decides what an address means

One small function, camera_source.py › parse_sourcehulikamote_backend/engine/camera_source.py:48, looks at the text and decides: a webcam number, a stream address, or a file. It refuses anything else, so a typed address can never be used to make the system open something it should not.

Step 3: reading the picture without falling behind

CameraSourcehulikamote_backend/engine/camera_source.py:72 is the part that talks to the camera. It has three jobs, and each one answers a problem from the first section.

  1. Do not wait forever. Connecting to a dead address must give up after a few seconds, and tell the user.
  2. Ask for the safe, low-delay way. Video over UDP can lose pieces on Wi-Fi and smear the picture, so we ask for TCP and for no buffering.
  3. Keep only the newest picture. A reader thread keeps taking pictures from the camera. When the AI is ready, it gets the latest one; older ones are dropped. Lag cannot pile up.
  4. Reconnect by itself. If the stream drops, wait 1, 2, 4, 8 seconds and try again, and show OFFLINE meanwhile.

How this is tested

31 automated tests cover this file, using a scripted fake camera (no network needed). They check what an address means, that the newest picture wins, that a silent camera gives up, that a dropped stream reconnects, and that stopping never releases a camera that is still being read.

The relay

Steps 4 and 5: from the AI to your screen

The AI loop is in stream.py › _real_loophulikamote_backend/routers/stream.py:196. For each picture it finds vehicles and runs the violation rules. The dashboard then needs two things: the data (boxes, tickets) and the picture. There are two ways to send the picture, chosen by HK_PICTURE_MODE:

ModeHow the picture travelsGood forWatch out
synced (default)A small JPEG inside the same message as the boxesBoxes that sit exactly on the vehicles. No encoder and no relay to go wrong.A bit more network and CPU per picture (fine on one computer)
relayFFmpeg compresses it (H.264) and sends it through MediaMTXSmooth video that also works for other viewersThe picture arrives later than the boxes, so the dashboard has to delay the boxes by eye
Why synced is the default

We first used only the relay. The picture took the longer way (encoder, relay, player) and showed up two seconds or more after the boxes, so the boxes ran ahead of the vehicles, and no fixed delay could cure it. Putting the picture in the same message makes it impossible for them to disagree.

The rest of this section is about the relay mode.

In relay mode, without the relay there is no picture, so the backend starts it by itself when it is installed in hulikamote_backend/tools/mediamtx.

Making sure the relay is running
A real bug we found and fixed (worth telling the panel)

When the relay was not running, the encoder could not send anywhere and stopped reading. The backend kept writing pictures into it, the pipe filled up, and the whole backend froze: uploads and Start hung for ever. The fix has two parts: pictures are handed to a separate writer thread through a small queue that drops pictures when it is full, and stopping kills the encoder first instead of waiting on it. An automated test makes a deliberately stuck encoder and checks that nothing blocks.

Only this thread can ever get stuck on the encoder

How to try it without a real CCTV

publish_clip.pytools/sim_cctv/publish_clip.py:1 plays a video clip as if it were a camera, with the same kind of address a real one gives. Run it on the same laptop, or on a second laptop on the same hotspot.

hulikamote_backend\venv\Scripts\python.exe tools\sim_cctv\publish_clip.py C:\path\to\clip.mp4 --mediamtx hulikamote_backend\tools\mediamtx\mediamtx.exe
  1. Copy the address it prints (like rtsp://192.168.1.20:8554/cam1).
  2. In the Live Monitor choose Change source, then Camera or phone..., and paste it.
  3. Press Test. It reports the picture size, speed and time to the first picture. The code is settings.py › test_video_sourcehulikamote_backend/routers/settings.py:165.
  4. Press Use this camera, then Start monitoring.

A phone works the same way: install an Android RTSP camera app, start it, and paste the address it shows. Use your own phone hotspot or router, not venue Wi-Fi, which often stops devices from seeing each other.

The honest version

What we claim, and what we do not

The claim

We do not claim that HULI-KAMOTE works on a real barangay CCTV. We surveyed how CCTV systems usually hand out their picture, built the Live Monitor to accept those inputs, and tested the same path with stand-in cameras. A real camera needs only its address.

Two honest limits: accuracy depends on the camera's angle and quality (blur, glare, small plates), and opening a barangay's CCTV needs their permission, the recorder's address and its password. The system only reads the picture; it has no pan, tilt, zoom or audio.

Terms used on this page

On screen, hover or tab to any dotted word for its meaning. This list is the same meanings, for the printed copy.

FFmpeg
A free tool that converts and compresses video.
frame
One still picture of a video. A video is many frames shown quickly, about 25 every second.
H.264
The most common way to compress video so it can travel over a network.
IP address
The number that tells a network where a device is, like 192.168.1.20. A network camera has one.
MediaMTX
A small free program that receives a video stream from one place and hands it to others. We use it as the relay between our AI and the dashboard.
MJPEG
A way to send video as a stream of ordinary JPEG pictures. Simple and widely supported, but it uses a lot of bandwidth.
ONVIF
An industry standard that lets cameras and software from different makers work together.
port
A numbered door on a device. One address can offer several services, each on its own door, for example 554 for camera video.
RTSP
Real Time Streaming Protocol: the way IP cameras and CCTV recorders send live video over a network.
stream
Video that is sent while it is being filmed, instead of a finished file.
VS Code
The code editor many developers use. The 'Open in VS Code' links jump straight to the line.
