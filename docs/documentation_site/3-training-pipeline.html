The whole pipeline in one picture

Training here is a loop, not a one-time job. Public data gives the models a start (steps 1 to 5). The system then runs on our own footage (7), is scored on clips with known answers (8), and its mistakes become new, human-checked training pictures (9) that go back into step 4. Each step has a script, so any of them can be repeated and audited.

Stage 1

Step 1. Collect: public data, mapped to our classes

Every source is one entry in a single list, the manifest. An entry says where to get the data, how its class names map to ours (a class that is not listed is dropped), its licence and country, and how much to trust it (trust grade). The script downloads it once, converts it to YOLO format, and merges it with a file-name prefix (<id>__), so running it again overwrites instead of duplicating.

One manifest entry (the Indian helmet photos)

python scripts/fetch_datasets.py                       # every model in the manifest

Stages 2 and 3

Steps 2 and 3. Clean the data and write it down

Raw public data is messy: broken files, boxes outside the picture, the same photo in training and in validation. Cleaning fixes what it can, moves (never deletes) what it cannot, and then writes a dataset card so nobody has to guess what is in a folder. This is the step that found the data leakage shown below.

python data.py curate --apply     # check + clean + standard layout (a dry run without --apply)
python data.py report            # DATASET_CARD.md for each dataset + CATALOG.md
python data.py sheet --staged ID # a picture grid with the boxes drawn, to look at a source by eye
Why the by-eye step matters

Project names lied: ph_plates is Vietnamese and colorum_plates is Indian, UK and US. Every Roboflow source was checked on a picture sheet before it was labelled Philippine or not. The command's own help says not to curate a model while it is training (the Training Studio and the terminal lab show which runs are active).

Stage 4

Step 4. Train: fine-tune a pretrained model

Training starts from yolov8n.pt, the small pretrained YOLOv8n, and continues learning on our dataset (fine-tuning). Every setting lives in one config file, so every run uses the same recipe unless a person overrides it on purpose. The learned settings of a finished run are saved next to it, in args.yaml (the settings) and results.csv (one line per epoch), which is where page 2's tables come from.

A rule learned the hard way

Do not edit files under hulikamote_backend/, and do not install packages into its environment, while a Studio-started training runs: the backend restarts and the training dies. This cost one helmet run (helmet_specialist/train, 19 epochs).

Hardware
A laptop with an NVIDIA RTX 3050 (6 GB). Under load its clock is power-capped, so trainings are slow: a car-matcher epoch of about 800 photos took about 30 seconds.
Why small models
YOLOv8n exports to about 12 MB and runs on this laptop; the pipeline is built to stay light (page 2).
Stages 5 and 6

Steps 5 and 6. Check the score, export, deploy

A model is checked before it is trusted. Each model has a target mAP@50 written in the validation script; the script prints PASS or FAIL. Ultralytics keeps the best epoch by fitness (10% mAP@50 plus 90% mAP@50-95), which prefers tight boxes over lucky ones. Then the model is converted to ONNX and copied where the backend looks.

Stage 9 · closes the gap to Zamboanga

Step 9. The harvest loop: our own footage, human-checked

Public data cannot teach what our cameras see. The harvest tool copies pictures from finished analyses, shows the model's guess, and asks a person to confirm or fix it, one picture at a time. Only a checked picture is ever added, and only while that model is not training. The rules are in code, not just in a README.

RuleWhy
A person checks every pictureWrong labels teach wrong things; the system's own guesses are never trusted unchecked.
Benchmark clips are protected (harvest.py protect <id>)A clip used to teach the model cannot also be used to score it.
The test split is never writtenOld and new models stay comparable.
Never writes inside hulikamote_backend/; never uploadsSafe while the backend runs; nothing leaves the machine.

Stage 8

Step 8. Benchmark: scoring the whole system, not just a model

A good detector does not guarantee a good system. mAP says how well boxes are found; the thesis also needs to know whether the right violation was logged for the right vehicle with the right plate. The benchmark runs clips whose real events a person wrote down through the same code the dashboard uses, and counts:

WordMeaningMetric
caughtA ticket of the same violation whose evidence time is within 3 s of a real event. Each ticket and event is used once.recall = caught / (caught + missed)
false alarmA ticket with no real event.precision = caught / (caught + false alarms); false alarms per minute
missedA real event with no ticket.recall
LOAROf the caught events, how many were logged with the right violation, vehicle and exact plate.the thesis' system metric
CER / WERHow wrongly plates were read: character errors, and the share of plates not exactly right.plate reading
Where the benchmark stands

The tool, the clip checklist and the dashboard tab are built and tested. The clip registry is still empty (284 backend tests pass, but there are no real-footage scores yet). A violation is only given a pass or fail once it has at least 10 real events; the others are reported as 'implemented, not scored'. Filling the registry from your own footage is the most valuable remaining task.

The defense

Why this pipeline is sufficient (and where it is not)

The honest one-sentence answer

This pipeline is sufficient to demonstrate what the thesis sets out to show: that automated, contactless traffic-violation detection is technically feasible with local, open tools. It is not yet sufficient to claim field accuracy on Zamboanga roads, because no model has been scored on real local footage; the loop that closes that gap is built, and the first local clip is in it.

How small are the things the models must find?

This is the argument for the cascade. Each number is the share of the whole picture that a typical labelled box covers.

DatasetSmallest 10%Typical (median)Biggest 10%
Vehicle set0.14%3.53%61.4%
Helmet set0.15%1.25%5.2%
Plate set0.02%0.31%3.8%
Cabin set0.16%1.38%18.5%

The plate model's typical target covers about a third of one percent of the picture. A single detector looking at a whole frame would see a few pixels. That is why the plate is searched inside a vehicle crop.

Questions the panel may ask, with short answers

Why YOLOv8n and not a bigger model?

It is small, fast and exports to a 12 MB file that runs on a laptop; the project aims to stay light enough for a barangay trial. The config says to move up to the 's' size if a score stays too low.

Why not one model for everything?

The objects differ hugely in size. A plate is a fraction of a percent of the frame. Cropping first lets each small model see its object large.

How do you know the scores are not inflated?

The cleaner found near-copies shared between training and validation or test, and removed the training copies. The test part is never written, and the best epoch is chosen by a strict score.

Your plate score is below target. Is the system usable?

Say so plainly: it is below target on the public validation set. The plate step is voted over up to 40 crops and read with format rules, and the plan to retrain on harvested local plates is built. Real read rates must be benchmarked.

Where is the accuracy on real roads?

Not measured yet, and we say so. The benchmark and clip checklist are built; the registry needs real clips. Claims are limited to violations with at least 10 real events.

Is the data legal to use?

Every source is listed with its licence and country (page 1). Most are CC BY 4.0 with credit; one is research-use only; unclear sources were excluded.

Terms used on this page

On screen, hover or tab to any dotted word for its meaning. This list is the same meanings, for the printed copy.

augmentation
Making extra training pictures by changing existing ones (flip, brighten, rotate, zoom) so the model copes with variety.
caught
A real violation that the system matched with a ticket of the same kind at about the same time.
CER
Character Error Rate: how many plate characters were read wrongly, as a share of all true characters.
data leakage
When the same (or almost the same) picture sits in both training and testing. The score then looks better than it really is.
early stopping
Stopping training when the score has not improved for a set number of epochs (called patience).
epoch
One full pass through all the training pictures.
false alarm
A ticket for something that did not really happen (a false positive).
fine-tuning
Training a pretrained model a little more on our own pictures so it learns our task.
fitness
The score Ultralytics uses to choose the best saved epoch: 10% of mAP@50 plus 90% of mAP@50-95.
harvest
Our tool that collects pictures from finished analyses so a person can check them and add them to a dataset.
LOAR
Logging and Organization Accuracy Rate: of the caught events, the share logged with the right violation, the right vehicle and the exact plate text.
manifest
A small list file that says which model file is active, or which datasets to download and how to map them.
mAP@50
mAP where a box counts as correct if it overlaps the true box by at least 50% (IoU 0.5). The score our thesis targets.
missed
A real violation for which the system made no ticket (a false negative).
mosaic
An augmentation that pastes four pictures into one, so the model sees objects in new surroundings.
near-duplicate
A picture that is almost identical to another one, such as the next frame of a video or a resized copy.
OCR
Optical Character Recognition: reading the letters and digits in a picture.
ONNX
A standard file format (.onnx) that stores a trained model so many programs can run it without the training software.
perceptual hash
A short fingerprint of how a picture looks. Pictures that look alike get fingerprints that are close.
Real-ESRGAN
A GAN-based super-resolution model that upscales pictures 4 times.
ReID
Re-identification: deciding whether two pictures show the same car.
training
Showing a model many pictures with the right answers, so it adjusts itself until it gives right answers by itself.
transfer learning
Re-using what a model learned on one task (everyday objects) to learn a new task (helmets) with much less data.
trust grade
Our own rating of a data source: A = peer-reviewed or official host, B = community upload with an open licence and a named author, C = unclear origin.
VS Code
The code editor many developers use. The 'Open in VS Code' links jump straight to the line.
WER
Word Error Rate: the share of plates that were not read exactly right (here a whole plate is one 'word').
YOLO
'You Only Look Once'. A fast family of object detectors that find all objects in a single pass over the picture.
YOLOv8n
The smallest ('nano') model of YOLOv8: about 3 million adjustable numbers, fast enough for a normal laptop.
